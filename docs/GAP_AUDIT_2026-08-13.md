# ATROPOS — Exhaustive Unimplemented Inventory

**Audited at:** commit `a327249` · 2026-08-13
**Authority:** Source Docs 1–4 · 100% Completion Blueprint · Core Engine Gap Map v2 · HOE UI/UX Gap Map v2 · Phase 20 Architecture Gap Map v2 · Superiority Addendum
**Tree measured:** 771 main Kotlin files · 306 test files · 202 registered commands

## How this was produced

Every component named in the source documents was searched for by symbol, then —
where found — checked for **production callers outside its own file**. That second
check is the one that matters. A component with a file and a passing test and zero
callers is not implemented; it is a stub with better camouflage, and it reads as
green on every metric that counts files or tests.

The gap maps are dated 2026-07-29. Substantial work has landed since, so their
status columns are stale in both directions — several atoms they mark OPEN are
closed, and several they assume present are orphaned. This document reflects the
tree, not the maps.

Four categories are used, ordered by how misleading each is:

| Category | Meaning |
|---|---|
| **DEFECT** | Claimed working; observed failing on the device |
| **ORPHANED** | Code + tests exist, zero production callers |
| **ABSENT** | No code at all |
| **UNENFORCED** | Exists, wired, but default-off or advisory |

## 6. Acceptance proofs never demonstrated

The blueprint's definition of 100% is proof-based, not code-based. None of the
seven Phase 20 crossover proofs has been run end-to-end on the installed runtime:

1. **Self-host proof** — ATROPOS closes a real ATROPOS requirement through its own loop and runs the newly installed JAR. *Sandbox proof exists; interactive-JAR mutation + git push path is unproven.*
2. **Greenfield factory proof** — one prompt creates, previews, tests, commits, packages **and deploys** a full-stack app. *Deployment half absent (§2.4).*
3. **Long-horizon proof** — multi-document workload continues across interruptions until all runnable nodes verify. *Never run.*
4. **Recovery proof** — process death restores exact claim, territory, worktree, evidence pointers, next action. *`RestartCoordinator` exists; the proof has not been executed.*
5. **Safety proof** — drift, secret leakage, out-of-territory change, self-verification, fake success, policy bypass all blocked. *No adversarial suite.*
6. **Fallback proof** — planning plugins and cloud providers disappear without destroying core planning. *Untested.*
7. **Learning proof** — evidence changes bounded routing/retry/batch weights while invariants hold. *Requires §2.3, which does not exist.*

Also unproven: **Phase 0** — fresh clone on Termux and clean CI producing the
same accepted JAR hash. Nothing records or compares JAR fingerprints across the
two environments.

## 7. Suggested order

The dependency order that unblocks the most, in sequence:

1. **D1** (memory StackOverflow) — cheapest fix, unblocks Phase 9 acceptance and every factory run's recall.
2. **D2** (lakehouse MISS) — the retrieval chain is built and reaches the store; only the last hop fails.
3. **§3 orphans** — wire `EvidenceCollector`, `LivePreviewService`, `VisualComparison`. These are already written; wiring them is small and converts four blueprint line items from false-green to true.
4. **§2.2 observability** — `ExecutionEvent` + `ProvenanceStream` + exporters. Everything in Phase 20 evaluation reads from this; building evaluation first would mean building it twice.
5. **§2.1 evaluation metrics** — now has a data source.
6. **§2.3 Phase 20 loop** — now has metrics to compute `I(p)` against.
7. **Web bridge endpoints** (`UI-DELTA-WEB-027`) — unblocks both Web and Android, since Android consumes the same bridge.
8. **§4 enforcement** — flip `ArchitectureComplianceChecker` to blocking only after the 55 oversized files are split, or the build stops immediately.
